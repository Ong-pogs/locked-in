## Design: legacy-deletion

### Ruling
RULING: The Phase-2 legacy-deletion design SURVIVES and is APPROVED for implementation, subject to the mandatory amendments below. All eight attack claims were verified against current master and are CONFIRMED; each is closed by a binding requirement. The deliverables are exactly three: PR-F (frontend), PR-B (backend stop-writes + route deletion + migration file 0046 committed-but-unapplied-to-prod), and a manual operator apply of 0046. Deploy order is PR-F first, PR-B second, 0046 last — this order is mandatory, not advisory.

BINDING DECISIONS (rationale for the implementer):

1. FAIL-CLOSED RECEIPT CONSTANTS, NOT SCHEMA CHANGES. lesson.miss_consequence_receipts is NOT touched by 0046. Its saver_count_before/after and extension_days_before/after are integer NOT NULL with no default (sql/0007_saver_consequence_runtime.sql:55-60), so they cannot be omitted from the INSERT pre-drop; instead applyMissConsequenceLocked writes literal 0 for all four. This decouples the money-critical miss path (daily lapse sweep + submit-time R13 catch-up → lapse_count → voucher bps) from every doomed runtime column in one move. Without this, the stop-writes deploy itself would halt the sweep and 500 grading — the single worst failure mode found.

2. THE COMPLETION UPDATE KEEPS ITS DAY/STREAK COLUMNS. applyVerifiedCompletionToCourseRuntime remains the writer of current_streak, longest_streak, and last_completed_day. Only gauntlet_active, gauntlet_day, fuel_counter, ichor_counter, ichor_lifetime_total leave the UPDATE. The design sentence "completion writes only streak + shields/lapse engine + course_completed_at" is amended accordingly: last_completed_day is what makes sameDay true and prevents +1-streak-per-lesson inflation of pot weight and leaderboard.

3. ensureCourseRuntimeState IS IN SCOPE DESPITE BEING AN INSERT. Its INSERT becomes (wallet_address, course_id) only. Safe pre-drop: fuel_cap has DEFAULT 7 (sql/0005:12) satisfying its check constraint (sql/0005:22). The design's "remove reads from all SELECTs" language is amended to "remove all references, read or write, to the ten dropped columns."

4. LEGACY WORKER: DISABLED BY ENV, CODE RETAINED. RUNTIME_SCHEDULER_ENABLED already defaults false (backend/src/config.mjs:169) and the worker is legacy-only (the fence at runtimeSchedulerWorker.mjs:133-148 skips v2-armed rows; the v2 lapse sweep is the separate shield-lapse-sweep.mjs Render cron and is untouched). With feedFireForCourse deleted, an enabled worker would burn ops-key fees on perpetual 100%-redirect record_redirect transactions for dead legacy fires — so the operator verifies the flag is unset/false on Render BEFORE PR-B merges. Legacy-PDA locks are thereby wound down: no further legacy harvests or legacy-worker misses (R13 catch-up still judges them on any submit, now with zeroed receipt constants). Unclaimed legacy yield in harvest_result_receipts is exported to CSV before deploy as bookkeeping; it is devnet-era value and is accepted as stranded once /brewery/claim is deleted.

5. FRONTEND REDIRECTS AND NAV REMOVAL ARE UNCONDITIONAL (judge override of the design's hasVaultV2Config gating). After PR-B, no backend in any environment serves brewery/shop/ichor endpoints, so a v1-world-preserving gate preserves only broken pages. /alchemy, /shop, /inventory page files remain as redirect stubs to /dashboard in all worlds; the three entries are removed from VillageScene, /menu, NAV_ITEMS, and BOTTOM_NAV_ITEMS outright. LegacyDashboard/LegacyDeposit/courseStore are left alone — the store's getters already coalesce missing fields to 0 (stores/courseStore.ts:154,159,164).

6. 0046 IS MINIMAL AND EXACT: one ALTER TABLE on lesson.user_course_runtime_state dropping exactly ten columns (ichor_counter, ichor_lifetime_total, fuel_counter, fuel_cap, fuel_fragments_today, fuel_fragments_day, gauntlet_active, gauntlet_day, saver_count, saver_recovery_mode), each DROP COLUMN IF EXISTS, preceded by SET LOCAL lock_timeout = '5s' (migrate.mjs wraps each file in BEGIN/COMMIT, so SET LOCAL is correctly scoped and a lock-timeout abort leaves the tracker unrecorded and the file cleanly re-runnable). Single-column check constraints on dropped columns auto-drop with them. Deliberately RETAINED for a later 0047: extension_days, fire_lit_until, last_brewer_burn_ts, last_fuel_credit_day, fuel_burn_cycle_receipts, harvest_result_receipts, all miss_consequence_receipts columns, and every v2/custody column — nothing outside the ten may be dropped in this phase.

7. THE 0046 APPLY IS A ROLLBACK POINT OF NO RETURN AND MUST NOT DANGLE. Verified: no auto-migrate hook exists (Render start is node src/server.mjs), but any future migrate.mjs run applies all pending files (migrate.mjs:289-311). Therefore: 0046 is applied to prod promptly after the PR-B soak (days, not weeks); no 0047+ may be authored against prod while 0046 is pending; before running migrate.mjs the operator confirms via dry-run that 0046 is the only pending file and that the LIVE Render deploy is the PR-B build or later; after apply, the Render rollback floor is the PR-B build forever. Before the apply, rolling the backend back to pre-PR-B is safe (old routes return; frontend redirects are backward compatible).

## Design: voucher-autoissue

### Ruling
RULING: The voucher-autoissue design is APPROVED WITH BINDING AMENDMENTS; the attacks' core findings are verified against the code and sustained. Three findings are dispositive: (1) In-transaction voucher persistence is REJECTED OUTRIGHT — including the SAVEPOINT fallback. The completing submit (backend/src/modules/progress/repository.mjs:4694 withTransactionAsWallet) is the money-adjacent path; db.mjs:69 never inspects the COMMIT result, so any swallowed in-tx SQL error silently converts the user's final-lesson submit into a ROLLBACK that reports success, and the pool-based issueCourseCompletionVoucher (repository.mjs:250, :259-264) cannot see uncommitted rows and throws 503 when unconfigured (:242-248). Voucher issuance moves to a best-effort post-commit hook, with the GET-position lazy heal and the existing POST as safety nets — a voucher failure may never touch lesson completion. (2) The stored/exposed payload MUST be the full 8-field CompletionVoucherResponse ({courseId, lapseCount, lock, authorityPubkey, bps, expiry, message, signature}) — the proposed 4-field shape is unusable by the client claim builder (web-app/services/solana/vaultV2.ts:294,302) — and pg's bigint-as-string expiry MUST be cast with Number() on every read. (3) The re-issue rule is extended to missing rows (heals pre-0046 completers via the 0043 backfill stamp) and NARROWED on drift: lapse_count is frozen at completion (repository.mjs:4865-4873, :4366; lapseSweep excludes completed rows), so a stored-bps mismatch is by definition a bug — the GET logs at error level and serves the stored voucher unchanged, never silently re-signing a finished user to a worse tier. All read-path signing is gated on position.status === 'ACTIVE' and voucherSigningConfigured(), attached in the route handler outside the 60s position cache, and wrapped so a DB blip yields voucher:null, never a 500. PROD-DEPLOY SEQUENCE (mandatory order): ship as ONE PR containing sql/0046 + backend code + tests; apply 0046 to prod Supabase via backend/scripts/migrate.mjs (dry-run, then apply) BEFORE merging to master, because Render autodeploys on push; the code must additionally be written to degrade to exactly today's behavior if the table is absent, making the ordering belt-and-suspenders rather than load-bearing. Rollback = revert the code; never DROP the table as rollback. No frontend change is required this release — the claim page's POST flow keeps working; consuming the embedded voucher is an optional follow-up that must retain the POST fallback. POT CYCLE: the §4.2 monthly cycle is SEVERED from this work and the existing machinery is FORBIDDEN for v2 — verified structural mismatches (legacy v1 PDA eligibility via lockVault.mjs:65-72 with a swallow-all catch at repository.mjs:3488, a PotWindow ledger v2 never feeds since vault_v2.rs:187 pays config.pot_vault directly, and a distributor paying from the wrong vault) mean running it would distribute nothing or from an unfunded account. It is a separate, blocking workstream with its own requirements below; until it ships, "full pot, payouts live in beta" is not true and forfeited USDC accumulating in the ops ATA must be monitored.
