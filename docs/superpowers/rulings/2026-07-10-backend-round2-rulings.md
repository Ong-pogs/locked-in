# Binding rulings — v2 backend round 2 (adversarial debate, 2026-07-10)

Judge rulings from the Fable adversarial debate. Implementers follow these verbatim.


## Design: enroll-on-deposit

### Ruling
APPROVED WITH BINDING AMENDMENTS. POST /v1/locks/:courseId/enroll ships — it is the correct fix for the invisible-lock HIGH (client-only Zustand enrollment) and every attack was verified against the code — but four parts of the original design are OVERRULED as written, and the endpoint may not merge without the scheduler fence in the same PR.

Overruled: (1) "status in {ACTIVE, PENDING}" — PENDING is never enrollable. open_lock_v2 initializes principal=0 and stamps lock_start_ts (programs/locked_in/src/vault_v2.rs:83-89) and lock_funds_v2 re-stamps lock_start_ts on activation (line 131), so PENDING-derived metadata is wrong by construction, and an abandoned PENDING would persist a $0 enrollment the future sweep punishes daily. PENDING and account-missing are the RPC-lag race (client confirms on its own connection, backend reads another node) and are handled as bounded retry, not acceptance. Also note CLOSED is unobservable: claim_v2 and force_return_v2 both carry close = owner (vault_v2.rs:493,539), so "account missing" is the settled state. (2) "the sweep/indexer can heal later" — no such healer exists (unlockIndexerWorker targets the old program; runtimeSchedulerWorker refuses to start off-devnet at runtimeSchedulerWorker.mjs:342). Replaced by a client pending-enroll retry plus a server-side lazy heal in GET /v1/locks/:courseId/position. (3) Enrollment-failure-as-toast without a pre-deposit gate — spec item 21 (relock of a completed course blocked forever) must be enforced BEFORE money moves via a new GET /v1/locks/:courseId/eligibility that DepositV2 must pass (fail closed: no response = no deposit), with the POST gate as the after-money backstop, because the PDA close+re-init makes on-chain relock always possible. (4) One attacker amendment is REJECTED in favor of a stronger rule: keying the engine-state reset to "the enrollments INSERT inserted a row" is not replay-safe in the presence of pre-existing enrollment rows and cannot distinguish relock-after-settlement. The binding reset key is on-chain lock identity: reset when the stored runtime lock_account_address is NULL or differs from the derived v2 PDA (first v2 arm, including legacy-PDA rows), or when the stored lock_start_at differs from the on-chain lock_start_ts at the same PDA (a new lock — reachable only by settling the old one, which already forfeits its yield, so reset is not exploitable); a replay against a live lock always sees identical PDA + identical immutable lock_start_ts and never resets. This kills both the legacy-punishment inheritance (consumeSaverOrApplyFullConsequence double-writes legacy saver state AND applyShieldLapseTransition, backend/src/modules/progress/repository.mjs:4025, feeding issueCourseCompletionVoucher's lapse_count read at :244-250) and the replay-reset exploit.

Blocking couplings: the legacy runtime scheduler fence (candidate query is `lock_account_address is not null ... order by updated_at asc` with batch default 5 — repository.mjs:1491-1493, config.mjs:171 — so five v2 enrollments starve ALL legacy harvest/miss processing, and syncCourseRuntimeStateWithLockSnapshot at repository.mjs:1406-1427 clobbers v2 custody columns for dual-lock wallets every ~15s) MUST land in the same PR as the endpoint. The miss-day uniqueness DDL and schema_migrations tracker (sql next free 0043; miss_consequence_receipts PK is per miss_event_id only, backend/sql/0007_saver_consequence_runtime.sql:62) BLOCK the §4.2 daily sweep, not this endpoint — the endpoint needs no DDL and ships first. Course validation runs before any RPC so the enrollments FK to lesson.courses (backend/sql/0001_lesson_platform.sql:201) can never surface as a 500 and lessonless placeholder courses (only 3 have content) can never be armed into guaranteed-lapse traps. All DB writes run inside withTransactionAsWallet because user_course_enrollments has FORCE row level security keyed to the request.jwt.claim.wallet_address GUC (backend/sql/0003_auth_progress_hardening.sql:41, backend/src/lib/db.mjs:51-56). The 60s position cache gains real seed/invalidate exports (today only a test hook exists, backend/src/lib/lockPosition.mjs:146) and enroll primes it so the course card cannot show a stale NONE for 60s after success. Every acceptance decision is made exclusively from server-derived data; the client's lockAddress is only a config-skew tripwire with its own loud error code, given this repo's documented program-ID skew history.

## Design: lapse-sweep

### Ruling
REJECTED AS WRITTEN; APPROVED AS AMENDED BELOW. All eight attacks are CONFIRMED against the code, not merely plausible. The design's population predicate selects an empty-for-v2, stale-for-v1 universe (lock_account_address's only writer is the devnet-gated v1 worker, repository.mjs:1409; no backend writer of user_course_enrollments exists); its lesson-day test uses an overwritten scalar (last_completed_day, :717) instead of the per-day record that already exists (verified_completion_events.completion_day); it shares no idempotency spine with the still-live miss engine (consumeSaverOrApplyFullConsequence applies the transition unconditionally behind a caller-keyed receipt, :3951-4025); it has no atomic day-claim, no catch-up, no completed-course exit, no on-chain liveness check, no streak persistence, and it ships schema ahead of the spec-mandated migration tracker. Any one of these mis-moves real money: lapse_count directly sets the signed voucher bps (issueCourseCompletionVoucher, :244-263), so a wrong miss-day is confiscation and a missed miss-day is unearned yield. The sweep CONCEPT is correct and required by spec 4.2 — a daily server-side judge of every completed UTC day per verified-ACTIVE lock — and is hereby ordered built with the binding requirements below. Governing principles, applied throughout: (1) fail closed on punishment — never apply a miss-day unless the lock is verified ACTIVE on-chain, the course is not complete, the day is a fully elapsed UTC day, and a day-keyed receipt was atomically claimed; (2) fail closed on absolution — never advance the sweep cursor past an unjudged day, and any skip (unreadable chain, PENDING window) must be explicit and logged; (3) one spine — miss idempotency lives in lesson.miss_consequence_receipts keyed by (wallet, course, miss_day) with event id auto-miss:{wallet}:{course}:{day}, shared by sweep, legacy worker, and internal endpoint; one transition writer, the exported applyShieldLapseTransition, never reimplemented; (4) schema drift is a deploy failure, not a silent dead cron. Ship order is R1 through R22 in numbered sequence; the Render cron (R16) must not be enabled until R6-R8 (registration) and R17-R18 (practice gate, completion exit) are live. Requirements R1-R22 are binding and to be followed verbatim.
